# hountybunter Phase 6: The Hunt View — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Start a real Claude Code session from the UI and work in it, with the
session bound to its transcript exactly rather than guessed — so what happens in
the browser and what the store records are the same session.

**Architecture:** `adapters/claude-code` gains a `spawnAgent` seam over
`node-pty`. The server keeps a registry of live PTYs; the browser streams output
over SSE and posts keystrokes back. Binding uses §7.4's resolution order, which
phase 4 made possible: spawn, wait for the first hook whose `cwd` matches, bind
its `session_id`, mark `exact`; with no hook, fall back to the newest transcript
in that directory and mark `guessed`.

**Tech Stack:** `@homebridge/node-pty-prebuilt-multiarch` (prebuilt binaries),
`@xterm/xterm` in the browser, SSE over the existing `node:http` server.

**Spec:** `docs/superpowers/specs/2026-08-27-hountybunter-design.md` §3.1, §3.2, §5, §7.4, §10

**Spike already done (2026-09-01).** node-pty installs from prebuilt binaries on
darwin arm64 / Node 22.14 with no build tools and no advisories; `claude`
2.1.235 runs under it with a real tty, window size propagated, exit 0. §14's
highest-rated install risk is retired for this machine — not for every machine,
so Task 1 keeps the failure legible.

## Global Constraints

- **The PTY runs the real `claude` binary.** Never the Agent SDK. That is what
  preserves the user's own subscription (§3.1) and what makes their installed
  plugins, skills, hooks, MCP servers, and CLAUDE.md apply unchanged. A session
  started from the UI must behave exactly like one started in a terminal.
- **Do not filter what the agent loads.** No `settingSources` equivalent, no
  curated plugin list. The tool observes an environment; it does not own one.
  What was loaded is *recorded* instead — `attr_plugin` and `attr_skill` already
  carry it.
- **Never mimic Claude Code's visual design.** (Spec §3.3) A terminal rendering
  the real CLI is the CLI's own output, which is fine; a hand-built lookalike
  chat UI is not.
- **A dead PTY is a state, not an error.** Process exits -> session marked
  ended, history retained and still readable. (Spec §10)
- **Guessed stays guessed.** If no hook arrives, the binding is a guess and the
  UI says so. Never present an inference as a fact. (Spec §7.4)
- **Still read-only on source code.** The agent inside the PTY edits files
  because the user told it to; hountybunter itself writes nothing but notes.
- **Out of scope:** pixels (phase 7), bounties (phase 8), drive mode (phase 9).

---

## The one decision this plan does not make

Whether the panel beside the terminal renders a **reading layer** — the
conversation re-drawn from the transcript as events, decisions, and remaining
work — or whether the terminal is the whole surface.

Both share everything in Tasks 1-6; the reading layer is additive and lands in
Task 7 only if wanted. It is deferred, not forgotten, because the answer depends
on living with the terminal first. What is already ruled out is a hand-built
chat UI that replaces the terminal: that needs the Agent SDK, which costs the
user's subscription (§3.1) and risks §3.3.

## Task 2: The live registry

- [x] **Step 1: Write the failing test** — starting a hunt returns an id; the
      registry finds it; killing it removes it; a bounded number of concurrent
      hunts is enforced with a message rather than an unbounded fork bomb;
      output is buffered so a client that connects late still sees what it
      missed.
- [x] **Step 2: Run test to verify it fails.**
- [x] **Step 3: Write minimal implementation.**
- [x] **Step 4: Run test to verify it passes.**
- [x] **Step 5: Commit** — `feat(web): keep a registry of live hunts`

**Changed while building.** "Killing it removes it" turned out to be wrong, and
the test caught it: a hunt that died is exactly what the user needs to look at,
so death is a state, not a disappearance. A killed hunt keeps its row and gains
`killedAt`; `exitCode` stays null until the process actually reports one, because
asking a process to end is not the same fact as it having ended. The slot frees
on `killedAt`, so the ceiling never wedges on a process still winding down.

## Task 3: Start, stream, type

- [x] **Step 1: Write the failing test** — `POST /api/hunts` with a cwd starts
      one and returns its id; `GET /api/hunts/:id/stream` emits SSE frames
      carrying output, including the buffered backlog first; `POST
      /api/hunts/:id/input` reaches the child; `POST /api/hunts/:id/resize`
      changes what the child reports; an unknown id 404s on all three.
- [x] **Step 2: Run test to verify it fails.**
- [x] **Step 3: Write minimal implementation.** SSE for output per §4's
      preference; a POST per keystroke is a sub-millisecond round trip on
      loopback, so the one-directional stream holds.
- [x] **Step 4: Run test to verify it passes.**
- [x] **Step 5: Commit** — `feat(web): stream a hunt and take input`

**Decided while building.** The request supplies the working directory and
nothing else. The command is the server's, from `HOUNTYBUNTER_AGENT_CMD` or
`claude` — this port has no auth by design (§2, one local user), and a
client-named binary would turn that into arbitrary local execution for anything
on the machine able to post a form.

`Response` grew a `stream` variant so a long-lived response is still built in
`routes.ts` and still testable without a socket; `serve.ts` only wires the
writer and unsubscribes on `close`.

## Task 4: Binding, in §7.4's order

- [x] **Step 1: Write the failing test** — a hunt with a matching hook binds
      that `session_id` and reads `exact`; a hunt with no hook falls back to the
      newest transcript in its directory and reads `guessed`; a hook arriving
      late still upgrades the binding; a hook for a different `cwd` never binds.
- [x] **Step 2: Run test to verify it fails.**
- [x] **Step 3: Write minimal implementation.**
- [x] **Step 4: Run test to verify it passes.**
- [x] **Step 5: Commit** — `feat(adapter): bind a spawned hunt to its transcript`

**Moved out of core.** Binding reads Claude Code's hook payload shape and its
transcript layout, which is what an adapter is for. Core keeps the hook table
and the `correlation` column; the adapter decides what they mean.

**Two things the plan did not anticipate.**

*The watermark.* Real hook payloads carry no timestamp — checked against a live
one — so "hooks that belong to this hunt" cannot be decided by time. The highest
hook id is taken at spawn instead, and only later hooks can match. It has to be
captured at spawn: a moment later, this hunt's hooks are indistinguishable from
those of a session that was already running in the same directory.

*Symlinks.* A directory reached through a symlink is reported by the agent as
its real location — on macOS every `/tmp` path is really `/private/tmp`. String
equality would miss every one, and a missed match reads as "no hooks installed",
which is the failure that looks most like normal operation. Both sides are
resolved before comparing.

The guess matches on the `cwd` inside the transcript's first line rather than on
the directory name Claude Code derives from a path: reproducing that transform
would be a second guess stacked on the first, and a near-miss would bind
confidently to the wrong project.

## Done when

A session started from the browser is indistinguishable from one started in a
terminal — same plugins, same skills, same subscription — and the store binds it
to its transcript exactly.

## Verification that is not a unit test

- Start a hunt, work in it for a real task, close the browser mid-session, and
  reopen: the terminal is still there and still attached.
- Kill the server while a hunt runs, and confirm the agent's own work is
  unaffected. The harness may lose its view; it must never take the session with
  it.
- Compare a hunt against a plain terminal session on the same task. Any
  difference in behaviour is a bug in the seam, not a feature.
